# SHA3-256: подробный разбор реализации и безопасности

Этот файл предназначен для изучения программы и подготовки к личной сдаче. Он разбирает текущие [src/sha3.h](src/sha3.h), [src/sha3.c](src/sha3.c), [src/main.c](src/main.c), [Makefile](Makefile), [scripts/demo.py](scripts/demo.py) и [tests/test_sha3.py](tests/test_sha3.py). Номера строк относятся к этим файлам на момент написания пояснений. Исходники программы не меняются при чтении или использовании этого документа.

## 1. Что программа делает с файлом

Команда `./build/sha3sum examples/small.txt` передаёт программе имя файла. Программа открывает этот файл, последовательно читает его байты, вычисляет SHA3-256 и печатает 32 байта результата в шестнадцатеричной форме. Каждый байт отображается двумя символами, поэтому строка хеша содержит 64 символа.

Хешируется содержимое файла. Имя, расширение, дата изменения, права доступа и расположение файла не входят в хеш. Если скопировать файл под другим именем, но сохранить все байты, результат останется тем же. Если добавить к `abc` перевод строки, входные данные изменятся и результат будет другим.

Слово «хеширование» здесь означает получение короткого отпечатка данных. Программа не шифрует файл и не предоставляет операции восстановления исходного содержимого из результата. Для произвольного входа такое однозначное восстановление невозможно: разных файлов больше, чем возможных 256-битных результатов.

Работа распределена между файлами:

| Файл | Ответственность |
| --- | --- |
| `src/main.c` | Получить аргумент, открыть и закрыть файл, обработать ошибки, вывести результат. |
| `src/sha3.h` | Объявить размер результата и контракт файловой хеш-функции. |
| `src/sha3.c` | Прочитать поток и выполнить собственный алгоритм SHA3-256. |
| `Makefile` | Собрать программу и запустить проверки. |
| `scripts/demo.py` | Показать сравнение малых и больших данных с эталоном в терминале. |
| `tests/test_sha3.py` | Автоматически проверить хеши и ошибочные сценарии. |

Общий путь выполнения:

```text
main
  -> проверка argc
  -> fopen(..., "rb")
  -> sha3_256_file
       -> нулевое состояние
       -> fread порциями до 8192 байт
       -> проверка ferror
       -> absorb: XOR байтов в состояние
            -> каждые 136 байт: keccak_f1600
       -> после EOF: finish
            -> дополнение последнего блока
            -> keccak_f1600
            -> извлечение 32 байт
  -> fclose
  -> вывод хеша и имени
  -> fflush и проверка вывода
  -> успешное завершение
```

## 2. Минимум языка C для чтения реализации

### 2.1. Типы и память

`unsigned char` используется для байтов. При принятом здесь условии `CHAR_BIT == 8` он хранит значения от 0 до 255. Байт `0x00` входит в бинарный файл наравне с другими байтами: программа не считает его концом данных. Символ конца C-строки `\0` имеет особое значение только при обработке строк, например имени файла.

`uint64_t` обозначает беззнаковый целый тип ровно на 64 бита, если платформа предоставляет этот тип. В таком слове помещаются восемь восьмибитных байтов. Для представления состояния алгоритма нужны 25 таких слов. Если платформа не предоставляет `uint64_t`, этот исходник не соберётся; перехода к неподходящему типу автоматически нет.

`size_t` обозначает беззнаковый тип, подходящий для размера объекта в памяти и индексов. Его предоставляет стандартная библиотека. На типичной 64-битной системе он имеет 64 бита, но код не предполагает конкретную ширину `size_t`.

Объявление `uint64_t lane[25]` выделяет место для 25 слов. Допустимые индексы этого массива: от 0 до 24 включительно. `lane[25]` уже выходит за границу. В C обычный доступ к массиву не выполняет автоматическую проверку границ, поэтому правильность индексов здесь нужно обеспечить кодом.

`Sha3Context *context` объявляет указатель на структуру. Выражение `context->pos` обращается к её полю `pos`; это сокращённая запись `(*context).pos`. Когда `context` объявлен локальной структурой, как в `sha3_256_file`, оператор `&context` получает адрес этой структуры для передачи функции. Если же `context` уже указатель, `&context` получает адрес самого указателя, что имеет другой тип и смысл.

В параметре функции запись `unsigned char digest[32]` фактически передаёт указатель, а не копию массива. Число 32 в такой декларации описывает ожидаемый размер для читателя, но не заставляет C проверить реальный размер памяти. Вызывающий код обязан передать подходящий массив. В `main` такой массив создаётся явно.

`const unsigned char *data` запрещает менять байты через этот указатель. Это не запрещает изменения той же памяти через другой указатель и не обеспечивает синхронизацию между потоками. В этой программе входной буфер изменяется только между вызовами `absorb`.

`static` перед функцией ограничивает её видимость текущим исходным файлом. Это полезно для внутренней реализации: другие файлы вызывают `sha3_256_file`, а не вмешиваются в порядок `absorb` и `finish`. `static const` у локальных таблиц означает постоянное время хранения и запрет изменений через это объявление; таблицы не создаются заново как обычные локальные массивы при каждом вызове.

### 2.2. Битовые операции

| Операция | Смысл | Пример на четырёх битах |
| --- | --- | --- |
| `a ^ b` | XOR: 1, когда соответствующие биты различаются. | `1010 ^ 1100 = 0110` |
| `a & b` | AND: 1, когда оба бита равны 1. | `1010 & 1100 = 1000` |
| `a \| b` | OR: 1, когда хотя бы один бит равен 1. | `1010 \| 1100 = 1110` |
| `~a` | NOT: инверсия каждого бита. | `~1010 = 0101` при ширине 4 бита. |
| `a << n` | Сдвиг влево на `n` разрядов. | `0011 << 1 = 0110` |
| `a >> n` | Сдвиг вправо на `n` разрядов. | `1100 >> 1 = 0110` для беззнакового типа. |

`a ^= b` означает `a = a ^ b`. XOR удобен для добавления блока в состояние: новые данные смешиваются с текущими битами, а не заменяют состояние. У XOR есть свойство `a ^ b ^ b = a`, но вся хеш-функция не сводится к XOR: между блоками работает сложная перестановка состояния.

Не путайте `|` и `||`: первый выполняет побитовое OR, второй проверяет логическое «или» условий. Аналогично `&` работает с битами, а `&&` с логическими условиями. `||` прекращает вычисление после первого истинного операнда; это называется сокращённым вычислением.

Оператор `%` возвращает остаток деления. Для неотрицательных индексов `x % 5` лежит в пределах от 0 до 4 и позволяет переходить между соседями по циклу. Например, сосед справа у столбца 4 имеет индекс `(4 + 1) % 5 = 0`.

`0x` обозначает шестнадцатеричное число. `0x06` равно 6 и записывается в двоичном виде как `00000110`. `0x80` равно 128 и записывается как `10000000`. Суффикс `U` в `64U` делает литерал беззнаковым. Макрос `UINT64_C(...)` создаёт целочисленную константу подходящего типа для 64-битных беззнаковых значений.

## 3. Как устроен SHA3-256 в этой программе

### 3.1. Состояние, rate и capacity

Здесь состояние представлено массивом из 25 слов по 64 бита: всего `25 * 64 = 1600` бит, или 200 байт. На вход между перестановками поступает по 136 байт. Эти 136 байт являются rate, то есть частью состояния, в которую XOR добавляет очередную порцию сообщения. Оставшиеся 64 байта составляют capacity и не принимают байты сообщения напрямую. Все 25 слов участвуют в перестановке, поэтому capacity не остаётся неизменной после начала работы.

Для SHA3-256 в этой реализации: `rate = 1088` бит, `capacity = 512` бит, результат = 256 бит. Обозначения алгоритма и его шагов можно сверить с [FIPS 202, разделы 3-6](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.202.pdf).

Внутри перестановки массив рассматривается как сетка `A[x,y]` размером 5 на 5. Каждая клетка является 64-битным словом, которое также называют lane. Формула размещения в одномерном массиве:

```text
index = x + 5*y

y = 0:  A[0,0] A[1,0] A[2,0] A[3,0] A[4,0] -> индексы  0..4
y = 1:  A[0,1] A[1,1] A[2,1] A[3,1] A[4,1] -> индексы  5..9
y = 2:  A[0,2] A[1,2] A[2,2] A[3,2] A[4,2] -> индексы 10..14
y = 3:  A[0,3] A[1,3] A[2,3] A[3,3] A[4,3] -> индексы 15..19
y = 4:  A[0,4] A[1,4] A[2,4] A[3,4] A[4,4] -> индексы 20..24
```

Например, `A[2,3]` находится в `lane[2 + 5*3]`, то есть в `lane[17]`. Первые 17 слов составляют 136 байт rate; остальные восемь слов дают 64 байта capacity.

### 3.2. Поглощение сообщения

В начале все слова состояния равны нулю. Для каждого входного байта определяется его позиция внутри текущего блока. Деление позиции на 8 выбирает слово; остаток деления на 8 выбирает место байта в слове. В состоянии байты располагаются от младших битов к старшим.

При `pos = 0` байт попадает в биты 0..7 слова 0. При `pos = 1` он попадает в биты 8..15 того же слова. При `pos = 8` выбирается слово 1 и его биты 0..7. При `pos = 135` выбирается слово 16 и биты 56..63. После этого обработано 136 байт: программа переставляет всё состояние и начинает новый блок с `pos = 0`.

Результат перестановки сохраняется. Начало нового блока не означает обнуление состояния. Именно сохранённое состояние связывает уже прочитанную часть файла со следующими байтами.

Буфер `fread` на 8192 байта и блок алгоритма на 136 байт имеют разные назначения. Первый уменьшает число обращений к файловому потоку, второй задан алгоритмом. Поскольку `8192 % 136 = 32`, граница чтения обычно попадает внутрь блока алгоритма. Поле `pos` сохраняется между чтениями и позволяет продолжить тот же блок из следующего буфера.

### 3.3. Что делает один раунд перестановки

`keccak_f1600` выполняет 24 раунда. Каждый раунд содержит пять операций в фиксированном порядке.

`theta` сначала XOR складывает пять слов каждого столбца. Из соседних сумм вычисляется поправка, которая XOR добавляется к каждому слову столбца. Одно из соседних значений предварительно поворачивается на один бит. Так данные из одних столбцов влияют на другие.

`rho` циклически поворачивает биты каждого слова на величину из таблицы. В отличие от простого сдвига, циклический поворот возвращает вышедшие слева биты справа, сохраняя все 64 бита.

`pi` переносит повернутые слова в другие клетки сетки. В коде `rho` и `pi` объединены: слово из `(x,y)` после поворота записывается в `(y, (2*x + 3*y) % 5)` массива `mixed`.

`chi` делает нелинейное смешивание внутри каждой строки. Новое слово зависит от старого слова и двух его соседей: `B[x,y] ^ ((~B[x+1,y]) & B[x+2,y])`, где индексы соседей берутся по модулю 5. Нелинейность связана с сочетанием NOT и AND. Все значения берутся из отдельного `mixed`, чтобы ранее записанный результат не стал входом для следующего слова той же строки.

`iota` XOR добавляет раундовую константу к слову `A[0,0]`. Константа меняется от раунда к раунду. Таблица содержит фиксированные значения алгоритма; она не является паролем или секретным ключом.

Каждый шаг по отдельности не следует представлять как самостоятельную гарантию криптографической стойкости. Реализуется вся заданная последовательность из 24 раундов. Совпадение результатов проверяется тестами.

### 3.4. Почему необходим padding

Хеширование не заканчивается сразу после последнего байта файла. В состояние нужно добавить окончание сообщения, которое отличает разные длины и задаёт область применения SHA-3. Для выровненных по байтам сообщений код XOR добавляет `0x06` в первую свободную позицию блока и `0x80` в последнюю позицию блока.

У `0x06` установлены биты 1 и 2. При чтении битов от младшего к старшему его начало выглядит как `0, 1, 1`: первые два бита задают суффикс SHA-3 `01`, следующий бит начинает дополнение `pad10*1`. У `0x80` установлен последний бит последнего байта блока. Между началом и концом дополнения идут нулевые биты сообщения. Формы дополнения для байтового входа приведены в [FIPS 202, приложение B.2, таблица 6](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.202.pdf).

Примеры описывают байты дополненного сообщения перед XOR со состоянием:

| Остаток длины по модулю 136 | Как дополняется последний блок |
| --- | --- |
| 0 | Новый блок: `06`, затем 134 нулевых байта, затем `80`. |
| 3 | Три байта сообщения, затем `06`, затем нули, в байте 135 находится `80`. |
| 134 | После сообщения остаются два байта: `06 80`. |
| 135 | Остаётся один байт: `06 XOR 80 = 86`. |

Позиции здесь считаются с нуля. Если файл имеет длину ровно 136 байт, его полный блок уже прошёл перестановку. Затем всё равно добавляется отдельный блок окончания. Если файл пустой, никакого блока данных нет, но блок окончания есть.

Состояние после предыдущей перестановки обычно содержит ненулевые значения даже в ещё не использованных позициях следующего блока. Их не нужно обнулять. Нулевой байт дополнения при XOR ничего не меняет, поэтому код не хранит массив padding и не делает цикл по его нулевой середине. Две операции XOR добавляют только ненулевые части окончания.

### 3.5. Извлечение результата

После добавления окончания выполняется ещё одна перестановка. Программа берёт первые 32 байта rate в том же порядке байтов, в котором добавляла сообщение: от младших байтов каждого слова к старшим. Результат полностью помещается в 136-байтовый блок выдачи, поэтому дополнительные перестановки для выдачи здесь не нужны.

Для файла из трёх байтов `abc` получаем:

```text
Вход: 61 62 63
Первое слово до перестановки с добавленным началом padding:
0x0000000006636261
Слово 16 дополнительно получает старший бит от окончания 0x80.
Затем: 24 раунда перестановки.
Хеш:
3a985da74fe225b2045c172d6bd390bd855f086e3e9d525b46bfe24511431532
```

Это пример начальной упаковки и конечного результата. Между ними состояние проходит все операции алгоритма; результат нельзя получить одним простым XOR входных байтов.

## 4. Построчный разбор `src/sha3.h`

Строки 1-2:

```c
#ifndef SHA3_H
#define SHA3_H
```

Строка 1 проверяет, что макрос `SHA3_H` ещё не определён. Строка 2 определяет этот макрос при первом подключении заголовка. При повторном `#include` содержимое до `#endif` будет пропущено. Это include guard: он исключает повторную обработку объявлений в одной единице трансляции. Это организация сборки, а не проверка входных данных во время выполнения.

Строка 4:

```c
#include <stdio.h>
```

Подключает стандартное описание файловых потоков, включая тип `FILE`, используемый в прототипе функции. Угловые скобки обозначают подключение заголовка через пути поиска системных заголовков.

Строка 6:

```c
enum { SHA3_256_DIGEST_SIZE = 32 };
```

Объявляет именованную целочисленную константу со значением 32. Имя используется при создании массива результата и в цикле выдачи. `enum` здесь не описывает набор состояний программы: это способ задать целочисленную константу времени компиляции, пригодную для размера массива.

Строки 8-14 представляют комментарий контракта. Строка 8 начинает многострочный комментарий, строка 14 завершает его. Строка 9 определяет операцию: читать от текущей позиции до EOF. Строка 10 возлагает открытие в бинарном режиме и закрытие потока на вызывающий код. Строка 11 требует доступной памяти минимум для 32 байт. Строка 12 описывает `0`, `-1` и `errno`. Строка 13 обещает не менять массив результата при отказе. Комментарий объясняет требования, но сам их не выполняет; их соблюдение обеспечивают реализация и вызывающий код.

Строка 15:

```c
int sha3_256_file(FILE *stream, unsigned char digest[SHA3_256_DIGEST_SIZE]);
```

Это прототип функции. `int` задаёт тип кода результата. `stream` указывает на открытый поток, `digest` на место для хеша. Точка с запятой завершает объявление; тела функции здесь нет. Благодаря этому `main.c` может вызвать функцию, реализация которой находится в другом файле.

Строка 17, `#endif`, закрывает условие из строки 1. Пустые строки служат только для разделения частей заголовка.

## 5. Построчный разбор `src/sha3.c`

### 5.2. `rotate_left`: циклический поворот

Строки 23-27 являются комментарием безопасности. Строка 23 начинает комментарий; строка 24 называет опасный сдвиг на 64; строка 25 объясняет отдельный случай нуля; строка 26 указывает использование беззнакового типа; строка 27 закрывает комментарий.

Строка 28:

```c
static uint64_t rotate_left(uint64_t value, unsigned int shift)
```

Объявляет внутреннюю функцию. Она принимает 64-битное значение и величину поворота, возвращает новое 64-битное значение. Исходная переменная вызывающего кода не меняется автоматически: параметры передаются по значению.

Строка 29, `{`, начинает тело функции.

Строка 30:

```c
return shift == 0 ? value : (value << shift) | (value >> (64U - shift));
```

Тернарный оператор имеет вид `условие ? результат_если_истина : результат_если_ложь`. Когда поворот равен нулю, функция сразу возвращает исходное значение. Выражение справа от двоеточия при этом не вычисляется. Это исключает вычисление `value >> 64`.

При `shift` от 1 до 63 левый сдвиг помещает основную часть битов на новые места, а правый сдвиг выделяет биты, вышедшие за левую границу. OR объединяет обе части. Если условно использовать слово на восемь битов, поворот `10000001` влево на один даст `00000011`: старший бит вернулся справа. В коде тот же принцип применяется к 64 битам.

Функция не проверяет произвольное значение `shift >= 64`. Безопасность её текущих вызовов опирается на известную таблицу 0..63 и вызовы с единицей. Это внутренняя функция, входной файл не задаёт величину поворота.

Строка 31, `}`, заканчивает тело функции.

### 5.5. `keccak_f1600`: rho и pi

Строка 75 является комментарием об объединении поворота и переноса слова.

Строка 76 начинает внешний цикл по строкам `y = 0..4`. Строка 77 начинает внутренний цикл по столбцам `x = 0..4`.

Строки 79-80:

```c
mixed[y + 5 * ((2 * x + 3 * y) % 5)] =
    rotate_left(state[index], rotation[index]);
```

Строка 79 выбирает клетку назначения. Её новая координата `x` равна старому `y`, новая координата `y` равна `(2*x + 3*y) % 5`. Строка 80 поворачивает исходное слово на число битов из `rotation[index]` и записывает результат в выбранную клетку. Знак `=` присваивает целое новое слово, а не XOR добавляет его.

Все клетки назначения различны. Чтобы это увидеть, обозначим новые координаты как `u = y` и `v = (2*x + 3*y) % 5`. Для каждого `u` исходный `y` известен; умножение на 2 по модулю 5 обратимо, потому что `2 * 3 % 5 = 1`. Поэтому исходный `x` однозначно восстанавливается как `3*(v - 3*u)` по модулю 5. Значит, обход 25 исходных клеток заполняет каждую из 25 клеток `mixed` ровно один раз. Для отрицательной промежуточной разности в этом математическом рассуждении нужен неотрицательный остаток; сам код прямого преобразования отрицательных значений не использует.

Строка 81 закрывает внутренний цикл по `x`. Строка 82 закрывает внешний цикл по `y`. Теперь весь `mixed` заполнен.

### 5.7. `absorb`: добавление входных байтов

Строки 98-102 являются комментарием безопасности. Строка 98 начинает его. Строка 99 описывает явную побайтовую упаковку; строка 100 противопоставляет её обращению через приведённый `uint64_t*` и называет выравнивание; строка 101 указывает strict aliasing и порядок байтов; строка 102 закрывает комментарий. Подробный пример этих рисков есть в разделе 10.

Строка 103:

```c
static void absorb(Sha3Context *context, const unsigned char *data, size_t size)
```

Объявляет внутреннюю функцию поглощения. `context` указывает на изменяемое состояние, `data` на входные байты, `size` задаёт число доступных байтов. `const` не даёт этой функции менять байты через `data`. Размер передаёт файловая функция из результата `fread`, а не из содержимого файла.

Строка 104 открывает тело. Строка 105, `for (size_t i = 0; i < size; ++i) {`, обходит ровно `size` байтов. Если `size == 0`, тело не выполняется, и доступ к `data[0]` не происходит.

Строка 106, `size_t pos = context->pos;`, получает текущую позицию в блоке. Локальная копия делает формулу следующей строки короче; состояние всё равно обновляется через `context`.

Строка 107:

```c
context->lane[pos / 8] ^= (uint64_t)data[i] << (8U * (pos % 8));
```

`data[i]` берёт очередной байт. Приведение к `uint64_t` выполняется до сдвига, поэтому сдвиг производится над 64-битным беззнаковым значением. `pos / 8` выбирает слово, `pos % 8` положение байта, умножение на 8 переводит это положение в число битов. XOR добавляет байт к состоянию.

При `pos < 136` индекс слова не превышает 16. Остаток `pos % 8` не превышает 7, поэтому сдвиг принадлежит набору `0, 8, 16, 24, 32, 40, 48, 56`. Он никогда не равен 64. Приведение после сдвига не дало бы такой защиты: промежуточный сдвиг мог бы выполняться над обычным `int`.

Строка 108, `++context->pos;`, увеличивает позицию на один после обработки байта.

Строка 109, `if (context->pos == SHA3_RATE) {`, проверяет заполнение блока. Значение 136 появляется только после обработки последнего допустимого байта, а не используется для доступа к следующему.

Строка 110 вызывает перестановку полного состояния. Строка 111 устанавливает `pos = 0` для следующего блока. При этом массив `lane` не обнуляется.

Строка 112 закрывает условие заполненного блока. Строка 113 закрывает цикл по байтам. Строка 114 закрывает функцию. При выходе `pos` снова находится в диапазоне 0..135.


Выбирает одно из первых четырёх слов состояния, сдвигает нужный байт в младшие восемь битов и преобразует значение к `unsigned char`. При таком преобразовании остаётся значение по модулю 256, то есть выбранный байт. На шаге `i = 0` это младший байт слова 0, на шаге `i = 31` старший байт слова 3. Наибольший сдвиг снова равен 56.

Строка 134 закрывает цикл извлечения. Строка 135 закрывает функцию. `finish` меняет состояние и не предоставляет возможности повторно продолжить поглощение: её вызывает файловая функция только один раз в конце.

### 5.9. `sha3_256_file`: потоковое чтение и ошибки

Строка 137:

```c
int sha3_256_file(FILE *stream, unsigned char digest[SHA3_256_DIGEST_SIZE])
```

Определяет единственную публичную функцию реализации. Её прототип уже находится в заголовке. Функция возвращает код результата; сам хеш возвращается через переданный массив.

Строка 138 открывает тело.

Строка 139, `Sha3Context context = {{0}, 0};`, создаёт локальное состояние. Вложенный `{0}` задаёт нулевое начало и по правилам инициализации обнуляет остальные элементы массива. Второй ноль задаёт `pos = 0`. Нулевыми оказываются все 25 слов, а не только первое. Это начало каждого нового независимого хеширования.

Строка 140, `unsigned char buffer[FILE_BUFFER_SIZE];`, выделяет локальный буфер на 8192 байта. Он не инициализирован заранее: функция читает только те его элементы, которые реально заполнил `fread`.

Строка 142, `if (stream == NULL || digest == NULL) {`, проверяет два явно неверных значения указателей. Если хотя бы один равен `NULL`, использовать его нельзя. Эта проверка не распознаёт висячие указатели, недостаточно большой массив или указатель на закрытый поток.

Строка 143 записывает `EINVAL`, то есть неверный аргумент. Строка 144 немедленно возвращает `-1`. Строка 145 закрывает условие. Выходной массив при таком отказе не изменяется.

Строки 147-150 являются комментарием безопасности: строка 147 связывает фиксированный буфер с размером файла; строка 148 указывает отсутствие выделения памяти по недоверенной длине; строка 149 указывает отсутствие общего переполняемого счётчика; строка 150 закрывает комментарий.

Строка 151, `for (;;) {`, начинает цикл без условия продолжения. Это осознанный бесконечный цикл: выйти из него можно через `break` после EOF либо через `return` при отказе. Он не должен заканчиваться после заранее рассчитанного размера файла.

Строка 152, `errno = 0;`, очищает старое значение ошибки перед чтением. Успешная операция не обязана обнулить `errno`, поэтому без этого шага можно было бы случайно сообщить причину от совершенно другой операции. Проверка успеха делается по `ferror`, а не по одному `errno`.

Строка 153:

```c
size_t count = fread(buffer, 1, sizeof buffer, stream);
```

`fread` принимает адрес, размер одного элемента, максимальное число элементов и поток. Здесь элемент равен одному байту. Поэтому возвращаемое число элементов одновременно является числом прочитанных байтов. `sizeof buffer` здесь получает фактический размер локального массива, 8192. Он не является размером указателя, потому что `buffer` объявлен массивом в этой функции.

Количество может быть меньше 8192 или равно нулю. Ноль сам по себе не сообщает, был ли достигнут конец файла или произошла ошибка. Для этого существуют индикаторы потока.

Строки 155-157 являются комментарием: строка 155 называет риск хеша усечённого файла; строка 156 объясняет проверку частичного чтения и неизменность `digest`; строка 157 завершает комментарий.

Строка 158, `if (ferror(stream)) {`, проверяет индикатор ошибки потока сразу после чтения. Даже если возвращены какие-то байты, установленный индикатор приводит к отказу. Такой вызов не заканчивается выдачей хеша прочитанного префикса.

Строка 159 проверяет, предоставила ли операция чтения ненулевую причину через `errno`. Строка 160 назначает `EIO`, общую ошибку ввода-вывода, если конкретной причины нет. Строка 161 закрывает внутреннее условие.

Строка 162 возвращает `-1` из всей функции. Строка 163 закрывает ветку ошибки. При возврате управление в `main` перейдёт к обработке отказа, а не к печати хеша.

Строка 164, `absorb(&context, buffer, count);`, передаёт адрес состояния, буфер и точное количество прочитанных байтов. Неиспользованный хвост массива не читается. Например, если последний `fread` заполнил только три байта, `absorb` выполнит три итерации.

Строка 165, `if (feof(stream)) {`, проверяет, обнаружило ли чтение конец файла. EOF проверяется после чтения. До первой попытки чтения `feof` обычно не сообщает, что файл пустой.

Строка 166, `break;`, выходит только из цикла чтения. Функция продолжит выполнение с `finish`. Строка 167 закрывает условие EOF.

Строка 168, `if (count == 0) {`, обрабатывает необычный случай: ноль байтов без EOF и без уже обработанной ошибки. Строка 169 назначает `EIO`, строка 170 возвращает `-1`, строка 171 закрывает ветку. Это не даёт крутиться в цикле без прогресса. Это не тайм-аут чтения: если сам `fread` блокируется, эта ветка до его возврата не выполняется.

Строка 172 закрывает цикл чтения. При нормальном завершении сюда попадаем после `break`.

Строка 173, `finish(&context, digest);`, впервые записывает хеш в выходной массив. Все чтения уже завершились без ошибки. Благодаря этому при более раннем отказе `digest` оставался нетронутым.

Строка 174 возвращает `0`, признак успеха API. Строка 175 закрывает функцию. Поток не закрывается здесь, потому что им владеет вызывающий `main`.

Если длина файла кратна 8192, последний успешный вызов `fread` может заполнить буфер полностью и ещё не установить EOF. Цикл сделает дополнительное чтение, получит ноль с EOF, вызовет `absorb` с нулевой длиной, выйдет и выполнит `finish`. Результат не зависит от того, обнаружен EOF на чтении последних байтов или на дополнительном чтении.

### 6.2. `print_path`: безопасный вывод имени

Строки 8-11 являются комментарием безопасности. Строка 8 называет управляющие символы в имени; строка 9 объясняет риск подделки вывода или управления терминалом; строка 10 фиксирует правило постоянной форматной строки; строка 11 завершает комментарий.

Строка 12:

```c
static void print_path(FILE *output, const char *path)
```

Объявляет внутреннюю функцию вывода имени файла в выбранный поток. Она используется и для нормального результата в `stdout`, и для сообщения об отказе в `stderr`. `const char *path` запрещает менять имя через этот параметр.

Строка 13 открывает тело.

Строка 14:

```c
const unsigned char *p = (const unsigned char *)path;
```

Создаёт указатель для побайтового обхода имени. `char` на некоторых платформах является знаковым: байт со значением 128..255 тогда мог бы выглядеть как отрицательное число и ошибочно удовлетворить условию `< 32`. Представление через `unsigned char` позволяет сравнивать именно значения байтов 0..255. Чтение представления объекта через символьный тип допустимо; это не опасное приведение буфера к многобайтовым словам.

Строка 16, `for (; *p != '\0'; ++p) {`, начинает обход C-строки. Инициализация в `for` отсутствует, потому что `p` уже установлен. `*p` читает текущий символ, сравнение с нулём обнаруживает конец строки, `++p` переходит к следующему байту. Имена, полученные через `argv`, представлены завершающимися нулём строками; встроенный NUL не входит в имя, передаваемое таким способом.

Строка 17, `switch (*p) {`, выбирает ветку в зависимости от текущего байта.

Строка 18:

```c
case '\\': fputs("\\\\", output); break;
```

Литерал `'\\'` представляет один обратный слеш. Строка `"\\\\"` содержит два обратных слеша: каждый из них в исходнике экранируется. Один слеш в имени отображается двумя видимыми слешами. Это позволяет отличить исходный слеш перед буквами от представления настоящего управляющего символа. `break` завершает текущую ветку `switch`, а не цикл обхода имени.

Строка 19, `case '\n': fputs("\\n", output); break;`, заменяет настоящий перевод строки двумя символами `\` и `n`. Имя не разбивает результат на несколько строк.

Строка 20 аналогично заменяет настоящий возврат каретки видимыми символами `\` и `r`. В C-литерале настоящая каретка записывается как `'\r'`, а строка с её видимым обозначением как `"\\r"`. Возврат каретки может переместить курсор к началу строки терминала, поэтому его не передают в терминал как управляющий байт.

Строка 21 заменяет настоящий символ табуляции `\t` видимыми слешем и `t`, чтобы имя не меняло выравнивание вывода.

Строка 22, `default:`, выбирает обработку всех байтов, для которых не было отдельного `case`.

Строка 23, `if (*p < 32 || *p == 127) {`, распознаёт оставшиеся ASCII-байты управления 0..31 и DEL со значением 127. Конец строки с байтом 0 уже остановил цикл раньше, поэтому в этой ветке обрабатываются остальные управляющие значения.

Строка 24:

```c
fprintf(output, "\\x%02x", (unsigned int)*p);
```

Выводит видимые символы `\x` и два шестнадцатеричных разряда значения байта. Например, ESC со значением 27 превращается в `\x1b`. Последовательность в имени уже не содержит фактического ESC, который мог бы начать управляющую команду терминала. `%02x` означает шестнадцатеричное число строчными буквами, ширину минимум 2 и заполнение нулями. Поскольку аргумент находится в пределах 0..255, получится ровно два разряда. Приведение к `unsigned int` согласует тип аргумента с `%x`.

Строка 25 закрывает условие и начинает `else` для остальных байтов.

Строка 26, `fputc(*p, output);`, выводит обычный байт без преобразования. Значения 128..255 также передаются как есть, чтобы не разрушать, например, последовательности UTF-8. Это не полная проверка или нормализация Unicode: имя может содержать визуально неоднозначные символы, а байты C1-диапазона 128..159 не экранируются отдельным правилом.

Строка 27 закрывает `else`. Строка 28 выполняет `break` для ветки `default`. Строка 29 закрывает `switch`; строка 30 закрывает цикл по строке; строка 31 закрывает функцию.

`print_path` не возвращает отдельно код ошибки записи. Для обычного результата `main` позже проверяет состояние всего `stdout` и выполняет `fflush`. При диагностике основной отказ уже установлен, поэтому программа в любом случае завершается с неуспехом. Если недоступен и `stderr`, доставку текста ошибки программа не гарантирует.

### 6.3. `report_error`: сообщение о причине отказа

Строка 33, `static void report_error(const char *action, const char *path, int error)`, объявляет внутреннюю функцию. Она принимает название действия, имя файла и заранее сохранённый код ошибки.

Строка 34 открывает тело.

Строка 35:

```c
fprintf(stderr, "sha3sum: %s '", action);
```

Выводит начало сообщения в `stderr`. `%s` получает текст действия, например `cannot open`. Форматная строка задана в программе. В текущих вызовах `action` тоже является фиксированной строкой из исходника.

Строка 36, `print_path(stderr, path);`, выводит имя через экранирование. Та же защита применяется к отказам, чтобы злонамеренное имя не подделывало диагностику.

Строка 37, `fprintf(stderr, "': %s\n", strerror(error));`, закрывает кавычку вокруг имени, выводит описание причины и завершает строку. Описание может зависеть от системы и локали. Переданное число `error` описывает исходный отказ, даже если промежуточные операции поменяли текущее `errno`.

Строка 38 закрывает функцию.

### 6.4. `main`: аргументы и открытие

Строка 40:

```c
int main(int argc, char *argv[])
```

Объявляет точку входа программы. `argc` содержит число аргументов, `argv` массив указателей на строки. При запуске `./build/sha3sum examples/small.txt` в `argv[0]` находится имя запуска, в `argv[1]` путь, а `argc` равно 2. Возвращаемый `int` становится кодом завершения процесса.

Строка 41 открывает тело. Строка 42, `unsigned char digest[SHA3_256_DIGEST_SIZE];`, выделяет 32 байта для результата. Они ещё не инициализированы, но читаются только после успешного вычисления, когда `finish` записал каждый байт.

Строка 44, `if (argc != 2) {`, требует ровно один входной путь. Без пути или с двумя путями программа не начинает хеширование. Проверка предшествует любому обращению к `argv[1]`.

Строка 45 выводит подсказку о формате запуска в `stderr`. `\n` внутри строкового литерала становится переводом строки в фактическом выводе. Имя команды в подсказке фиксировано, поэтому даже необычное `argv[0]` не попадает в диагностику.

Строка 46 возвращает `EXIT_FAILURE`, а строка 47 закрывает условие. В проверенной системе это код 1. Для стандартного C значим именно признак неуспешного завершения, заданный макросом.

Строка 49 является комментарием о бинарном режиме чтения.

Строка 50:

```c
FILE *input = fopen(argv[1], "rb");
```

Открывает переданное имя для чтения. `r` означает read, `b` binary. На системах, где текстовый режим преобразует переводы строк, бинарный режим исключает это преобразование. На POSIX различие обычно не проявляется, но явное `b` сохраняет смысл программы при переносе.

Программа не вызывает shell и не выполняет имя файла как команду. Кавычки в пользовательской команде нужны оболочке, чтобы передать путь с пробелами одним аргументом. После этого `fopen` получает уже готовую строку пути.

Строка 51, `if (input == NULL) {`, проверяет отказ открытия. Причиной может быть отсутствие файла или недостаток прав.

Строка 52 вызывает `report_error` с действием `cannot open`, именем и текущим `errno`. Значение `errno` передаётся как аргумент до операций внутри функции диагностики.

Строка 53 завершает процесс с отказом. Строка 54 закрывает условие. `fclose` здесь не вызывается, потому что открытого потока нет.

### 6.5. `main`: хеширование и освобождение ресурса

Строка 56, `if (sha3_256_file(input, digest) != 0) {`, вызывает алгоритм и проверяет результат. Если функция вернула `-1`, нужно закрыть открытый поток и сообщить причину, не читая неготовый `digest`.

Строка 57:

```c
int error = errno; /* fclose может изменить errno. */
```

Сохраняет причину отказа чтения в отдельной переменной. Встроенный комментарий объясняет порядок: следующий `fclose` может сам установить другое значение `errno`. Без сохранения пользователь мог бы получить причину закрытия вместо причины исходного отказа.

Строка 58, `(void)fclose(input);`, пытается закрыть поток даже после ошибки чтения. Приведение к `void` явно показывает намеренное игнорирование результата закрытия в этой ветке. Главной причиной отказа уже остаётся ошибка чтения. Это не означает, что вообще все результаты `fclose` игнорируются.

Строка 59 выводит ошибку `cannot read` с сохранённым значением `error`. Строка 60 возвращает отказ. Строка 61 закрывает ветку.

Строка 62, `if (fclose(input) != 0) {`, закрывает поток после успешного вычисления и проверяет результат. Успешное `fclose` возвращает 0. При отказе закрытия программа выбирает консервативное поведение: не печатать успешный итог.

Строка 63 выводит `cannot close` с причиной. Строка 64 возвращает отказ. Строка 65 закрывает условие. После вызова `fclose` программа не использует `input` повторно и не пытается закрыть его ещё раз.

В нормальном пути один успешный `fopen` соответствует одному `fclose`. В пути отказа чтения тоже выполняется одна попытка закрытия. Это управление ресурсом на уровне данной функции; оно не является доказательством отсутствия всех внутренних выделений памяти библиотекой C.

### 6.6. `main`: печать и завершение

Строка 67 начинает цикл по 32 байтам готового хеша.

Строка 68:

```c
printf("%02x", (unsigned int)digest[i]);
```

Печатает текущий байт двумя шестнадцатеричными символами. Аргумент явно приводится к `unsigned int`, типу для спецификатора `%x`. Например, байт со значением 3 печатается как `03`, а 255 как `ff`. Все 32 итерации создают 64 символа подряд без пробелов между байтами.

Строка 69 закрывает цикл. Строка 70, `fputs("  ", stdout);`, добавляет два пробела между хешем и именем. Строка 71 выводит имя через `print_path`. Строка 72 добавляет один настоящий перевод строки, который задаёт сама программа.

Строки 74-76 являются комментарием безопасности: строка 74 объясняет ненулевой код при отказе вывода; строка 75 объясняет роль `fflush` для буферизованной записи; строка 76 закрывает комментарий.

Строка 77:

```c
if (fflush(stdout) == EOF || ferror(stdout)) {
```

Принудительно передаёт накопленные байты потока вывода нижележащему механизму записи и проверяет ошибку. Успешные на вид вызовы `printf` могли только наполнить буфер в памяти. Реальная проблема, например переполненное устройство вывода, может обнаружиться при сбросе буфера. Если `fflush` уже вернул `EOF`, логическое `||` не вычисляет второй операнд, но условие всё равно истинно. Иначе `ferror` проверяет ошибки, возникшие раньше.

Строка 78 пытается вывести сообщение `cannot write output` в `stderr`. Строка 79 возвращает отказ. Строка 80 закрывает условие.

Строка 81 возвращает `EXIT_SUCCESS`. Этот путь достижим только после успешных аргументов, открытия, полного чтения, вычисления, закрытия входа и вывода. Строка 82 закрывает `main`.

Сброс буфера не обеспечивает атомарность вывода: часть строки могла успеть попасть в приёмник до обнаружения ошибки. Он также не делает `fsync` и не обещает сохранность перенаправленного результата при сбое питания. При закрытом pipe система может завершить процесс сигналом SIGPIPE; специальный обработчик для него здесь не устанавливается.

## 7. Построчный разбор Makefile

### 7.1. Что происходит при сборке

Компилятор сначала обрабатывает `src/main.c` и `src/sha3.c` отдельно, создавая объектные файлы. В них ещё могут оставаться ссылки на внешние функции. Затем линкер связывает объектные файлы и стандартную библиотеку в исполняемый `build/sha3sum`.

`make` следит за зависимостями и временем изменения файлов. Если объектный файл старше своего исходника или заголовка, он пересобирается. Изменение самого Makefile не описано как зависимость объектных файлов, поэтому после смены флагов сборки следует выполнить `make clean` и заново `make`.

### 7.2. Переменные и цели

Строка 1, `CC ?= cc`, задаёт запасное имя компилятора, если переменная ещё не определена. У GNU Make часто уже есть встроенное значение `CC = cc`, поэтому в таком случае эта строка его сохраняет. Можно выбрать другой компилятор командой `make CC=gcc`.

Строка 2, `PYTHON ?= python3`, задаёт интерпретатор для тестов и демонстрации при отсутствии другого значения.

Строка 3, `CPPFLAGS ?=`, предусматривает дополнительные флаги препроцессора, например пути подключения заголовков. Пустое значение здесь допустимо.

Строка 4, `CFLAGS ?= -O2`, задаёт оптимизацию для обычной сборки. `-O2` не является отдельной защитой от уязвимостей: это настройка генерации машинного кода.

Строка 5, `LDFLAGS ?=`, предусматривает флаги линкера. Строка 6, `LDLIBS ?=`, предусматривает подключаемые библиотеки. Для текущей программы дополнительные криптографические библиотеки не нужны.

Строка 7:

```make
WARNINGS = -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -Wformat=2
```

`-std=c11` выбирает стандарт языка, который поддерживает `_Static_assert`. Остальные флаги включают диагностику потенциальных ошибок:

- `-Wall` включает распространённые предупреждения, но не буквально все существующие.
- `-Wextra` добавляет ещё проверки к `-Wall`.
- `-Wpedantic` диагностирует некоторые отклонения от выбранного стандарта.
- `-Wconversion` помогает заметить неявное изменение диапазона или знака при преобразовании типов.
- `-Wshadow` помогает заметить, что новая переменная скрыла другую с таким же именем.
- `-Wformat=2` усиливает проверки форматных вызовов вроде `printf`.

Эти предупреждения помогают обнаружить ошибки при сборке, но не запрещают запуск каждой потенциально неверной программы. Флага `-Werror`, превращающего предупреждения в ошибки, здесь нет. Наблюдавшаяся сборка не выдала предупреждений.

Строка 8, `OBJECTS = build/main.o build/sha3.o`, задаёт список объектных файлов для линковки и очистки.

Строка 10, `.PHONY: all test sanitize demo clean`, отмечает цели-действия, для которых существующий файл с тем же именем не должен отменять выполнение. Например, случайный файл `test` не помешает запуску тестов.

Строка 12, `all: build/sha3sum`, делает обычную сборку первой пользовательской целью. Поэтому `make` без имени цели собирает `build/sha3sum`.

Строка 14, `build:`, объявляет цель для каталога сборки. Строка 15, `mkdir -p build`, создаёт каталог при необходимости. `-p` позволяет не считать уже существующий каталог ошибкой. Здесь каталог является реальным объектом файловой системы и не указан как `.PHONY`.

Строка 17:

```make
build/%.o: src/%.c src/sha3.h | build
```

Это шаблонное правило: `%` заменяется одним и тем же именем в цели и исходнике. Например, `build/main.o` зависит от `src/main.c` и `src/sha3.h`. Символ `|` задаёт зависимость порядка: каталог `build` должен существовать, но изменение времени самого каталога не является причиной пересобрать объект.

Строка 18:

```make
$(CC) $(CPPFLAGS) $(CFLAGS) $(WARNINGS) -c $< -o $@
```

Запускает компилятор с переменными флагов. `$<` обозначает первую зависимость, конкретный `.c`; `$@` имя текущей цели, конкретный `.o`. `-c` создаёт объект без линковки; `-o` задаёт файл результата. Строка рецепта начинается табуляцией: Makefile использует её как признак команды.

Строка 20, `build/sha3sum: $(OBJECTS)`, объявляет зависимость исполняемого файла от двух объектов.

Строка 21 запускает компилятор как драйвер линковки. `LDFLAGS` передаются для связывания, затем идут объекты, после них `LDLIBS`, затем имя результата через `-o $@`. В этом вызове нет `-c`, поэтому создаётся исполняемый файл.

Строка 23, `test: build/sha3sum`, требует собрать программу перед тестами. Строка 24 запускает Python-тесты и передаёт путь к обычной сборке через `--binary`.

Строка 26 объявляет отдельный исполняемый файл санитайзеров с зависимостью от обоих `.c`, заголовка и наличия каталога.

Строка 27:

```make
$(CC) $(CPPFLAGS) $(WARNINGS) -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer src/main.c src/sha3.c $(LDFLAGS) $(LDLIBS) -o $@
```

Собирает и связывает оба исходника сразу. `-O1` оставляет умеренную оптимизацию, `-g` добавляет отладочные сведения, `-fsanitize=address,undefined` добавляет проверки памяти и ряда неопределённых операций. `-fno-omit-frame-pointer` помогает получить понятные стеки вызовов. Эта цель использует собственный набор `-O1 -g`, а не обычный `CFLAGS`. Это отдельный диагностический бинарник; обычный `build/sha3sum` не становится автоматически инструментированным.

Строка 29 требует сборку диагностического бинарника для цели `sanitize`. Строка 30 запускает тот же Python-набор, но с путём к этому бинарнику. Это проверка того же поведения в другом режиме сборки.

Строка 32 требует обычный бинарник для `demo`. Строка 33 запускает демонстрацию в терминале. Она не создаёт HTML или отчёты.

Строка 35 объявляет очистку. Строка 36, `$(RM) $(OBJECTS) build/sha3sum build/sha3sum-sanitize`, удаляет только перечисленные файлы сборки. У GNU Make `RM` обычно равно `rm -f`. Очистка не использует рекурсивное удаление каталога проекта, не удаляет исходники и сохраняет примеры входных файлов.

## 10. Что сделано для безопасности

### 10.1. Какие входы считаются недоверенными

Недоверенными для этой утилиты являются путь, который передал пользователь, содержимое файла и поведение операций ввода-вывода. Путь может содержать неожиданные байты. Файл может быть пустым, очень большим, бинарным или недоступным. Устройство чтения или вывода может завершиться ошибкой.

Из содержимого файла программа не берёт адреса памяти, размер выделения, число раундов, индексы таблицы или форматные строки. Байты файла используются только как значения для XOR. Тем самым вход не получает прямого контроля над этими параметрами реализации.

Ниже разобраны конкретные ошибки, которые предотвращает текущий код. Это описание мер и их границ, а не заявление, что у программы принципиально не может быть уязвимостей.

### 10.2. Переполнение буфера и доступ за границы

Потенциальная проблема: выделить небольшой массив, прочитать в него больше данных или использовать индекс, взятый из файла. В C запись за границу может повредить соседнюю память, привести к аварии и в некоторых программах открыть путь к выполнению чужого кода.

Мера в этой реализации: `fread` получает максимальный размер `sizeof buffer`, а `absorb` получает возвращённое `count`. Чтение в массив ограничено 8192 байтами, обход входа ограничен именно заполненной частью. Общий размер файла не используется для разовой записи в этот буфер.

Проверка индексов по формулам:

| Место | Ограничение | Максимальный индекс |
| --- | --- | --- |
| `buffer[i]` в `absorb` | `i < count`, `count <= 8192` | 8191 для заполненного буфера. |
| `lane[pos / 8]` | `0 <= pos <= 135` | 16 при размере `lane` 25. |
| `state[x + 5*y]` | `x,y` в 0..4 | 24 при размере 25. |
| `column[(x + k) % 5]` | Остаток в 0..4 | 4 при размере 5. |
| `mixed[y + 5*((2*x+3*y)%5)]` | Обе координаты в 0..4 | 24 при размере 25. |
| `rotation[index]` | `index = x + 5*y` | 24 при размере 25. |
| `round_constant[round]` | `round` в 0..23 | 23 при размере 24. |
| `digest[i]` при выдаче | `i` в 0..31 | 31 при требуемом размере 32. |

Внешний контракт массива остаётся существенным. `sha3_256_file` не может определить реальную вместимость `digest` по обычному указателю. Внутренний `main` передаёт правильный массив. Если сторонний код вызовет API с памятью на один байт, это нарушение контракта и проверка `NULL` его не обнаружит.

Проверка: граничные файлы и AddressSanitizer упражняют фактически выполненные обращения к памяти. Они дополняют рассуждение об индексах, но не доказывают правильность любого возможного стороннего вызова API.

### 10.3. Расход памяти на больших файлах и счётчики

Потенциальная проблема: сначала получить размер файла, выделить под него память целиком, неверно вычислить размер или исчерпать память очень большим входом. Переполнение при вычислении размера может привести к слишком маленькому выделению с последующей записью за пределы.

Мера: собственная реализация C не вызывает `malloc` по размеру файла и читает последовательно. Её локальный входной массив всегда содержит 8192 байта. Состояние содержит 200 байт данных плюс поле позиции и возможное выравнивание. В перестановке дополнительно нужны 40 байт `column` и 200 байт `mixed`; точный размер стека зависит от компилятора. Библиотека C может иметь собственный буфер потока, но он тоже не увеличивается в коде пропорционально всему файлу.

`pos` считает только байты текущего блока и сбрасывается при 136. Счётчика общей длины нет. Поэтому нет операции вида `total += count`, которая могла бы переполниться на очень длинном потоке. Все циклы по входному буферу ограничены его фиксированным размером.

Время работы растёт с числом прочитанных байтов и числом блоков. Фиксированная память не ограничивает длительность: огромный файл может долго хешироваться. Бесконечный поток или блокирующее устройство может не завершиться. Ограничения времени и размера для публичного сервиса здесь не реализованы; это локальная файловая утилита.

### 10.4. Неопределённое поведение сдвигов

Потенциальная проблема: вычислить сдвиг на ширину типа или больше, выполнить опасный знаковый сдвиг либо сначала сдвинуть байт как `int`, а потом расширить результат. Неопределённое поведение позволяет компилятору получить результат, на который автор программы не рассчитывал.

Меры в текущем коде: слова имеют тип `uint64_t`; поворот на ноль выделен в отдельную ветку; остальные повороты заданы таблицей 1..63; сдвиги байтов ограничены 0..56; входной байт преобразован в `uint64_t` до операции. Правило недопустимости сдвига на ширину типа можно сверить с [SEI CERT C, INT34-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/integers-int/int34-c/).

Пример опасной формы для иллюстрации, она не используется в программе:

```c
/* В этой форме расширение происходит слишком поздно. */
uint64_t value = (uint64_t)(data[i] << 56);
```

Если `data[i]` сначала продвинут до 32-битного `int`, сдвиг на 56 уже некорректен. Правильная форма текущей реализации:

```c
uint64_t value = (uint64_t)data[i] << 56;
```

Это учебное сравнение выражений; переменная `value` в таком виде не добавлялась в исходник. UBSan помогает обнаруживать ряд неверных сдвигов во время реально выполненных путей. Он не меняет требований самого языка.

### 10.5. Выравнивание, aliasing и порядок байтов

Потенциальная проблема: трактовать восемь байтов входного буфера как готовый `uint64_t`, например через `*(const uint64_t *)data`. Полученный адрес может быть не выровнен для этого типа. Также тип объекта и правила доступа к нему могут не разрешать такое чтение. Даже если обращение работает на конкретном процессоре, значение зависит от его порядка байтов.

Мера: программа получает каждый байт как `unsigned char`, расширяет численно и сдвигает на определённую позицию. Она не выполняет загрузку многобайтового слова из приведённого адреса буфера. Аналогично выдача хеша выполняется числовыми сдвигами и преобразованием к байту. Требуемый little-endian является порядком упаковки алгоритма, а не предположением о физическом хранении слов в памяти процессора.

`_Static_assert(CHAR_BIT == 8)` отсекает неподходящее представление C-байта. Текущие тесты запускались на имеющейся платформе. Отдельный запуск на big-endian машине не выполнялся, поэтому переносимость здесь обоснована способом упаковки, а не подтверждена испытаниями на всех архитектурах.

### 10.6. Неинициализированная память

Потенциальная проблема: читать остатки стека как часть состояния или включить непрочитанный хвост буфера в хеш. Результат тогда зависел бы от посторонних данных, мог стать неповторяемым или раскрыть сведения о памяти процесса.

Меры: все слова `context` явно обнуляются; `absorb` получает точный `count`; каждый `column` заполняется перед использованием; преобразование pi заполняет весь `mixed`; `finish` записывает все 32 байта `digest` перед его успешным выводом. В пути ошибки `main` не печатает неинициализированный выходной массив.

Это объясняет, почему предварительное обнуление `buffer`, `column`, `mixed` и `digest` не требуется для правильности текущего потока данных. Отдельная защита от чтения освобождённой памяти в стороннем некорректном вызове API этим не обеспечивается.

### 10.7. Хеш недочитанного файла

Потенциальная проблема: цикл закончился из-за ошибки диска, но программа восприняла это как EOF и выдала успешный хеш первых прочитанных байтов. Пользователь получил бы отпечаток другого сообщения, хотя имя в строке результата осталось бы прежним.

Мера: каждый `fread` сопровождается проверкой `ferror` до дальнейшей обработки и до `finish`. Окончание вычисляется только при выходе по EOF. При ошибке массив результата не записывается, а `main` завершает процесс без строки хеша.

Сохранение `errno` перед `fclose` оставляет правильную исходную причину в диагностике. При отсутствии конкретного кода используется `EIO`. Проверка нулевого чтения без EOF исключает цикл без прогресса после возврата `fread`.

Проверка: тест чтения каталога упражняет отказ `fread` в Linux. Сбой после нескольких успешных буферов и специальный случай частичного результата с одновременным `ferror` отдельно не имитировались; их обработка следует из порядка веток в исходнике.

### 10.8. Корректное окончание SHA-3

Потенциальная проблема: неправильно дополнить последний блок, пропустить отдельный блок после точной кратности или использовать суффикс другого варианта Keccak. Получился бы детерминированный результат, но не SHA3-256, ожидаемый принимающей стороной.

Мера: `finish` добавляет `0x06` и `0x80` через XOR, вызывает перестановку и извлекает 32 байта. Однобайтовый остаток даёт `0x86`, точный блок получает отдельное окончание. Входные байты не рассматриваются как строка и не обрезаются на NUL.

Проверка: известные результаты пустого сообщения и `abc`, все остатки длины блока, 135/136/137 и 271/272/273 байта, бинарные и большие файлы. Здесь корректность алгоритма связана с безопасностью применения: неправильный вариант или усечённые данные делают сравнение целостности бессмысленным. Это не утверждение, что различие суффиксов само по себе является найденной атакой на SHA-3.

### 10.9. Форматные строки и терминал

Потенциальная проблема форматной строки: вызвать `printf(path)`. Тогда `%s`, `%n` и другие последовательности внутри пользовательского имени интерпретировались бы функцией форматирования. Последствия могут включать чтение неверных адресов или запись через неподходящий аргумент.

Мера: все форматы `printf` и `fprintf` фиксированы в исходнике. Имя передаётся побайтово в `print_path`, а не используется как формат. Для чисел `%x` применяется с аргументом `unsigned int`. `%s` внутри имени остаётся обычными символами.

Потенциальная проблема терминала: настоящее LF создаёт лишнюю строку результата, CR может переместить курсор, а ESC может начать управляющую последовательность. Мера: ASCII-управление и DEL печатаются видимыми обозначениями; обратный слеш также экранируется. Та же функция обслуживает stderr.

Проверка: созданный тестовый файл содержит `%s`, слеш, LF, CR, TAB, ESC и DEL. Проверяется точный stdout, отсутствие настоящего ESC в stderr и единственная завершающая строка диагностики.

Граница: это экранирование выбранных байтов, не полноценный анализ безопасности произвольного терминала и Unicode. Байты 128..255 сохраняются; графически похожие буквы, двунаправленные символы текста и ошибочные кодировки не нормализуются. Вывод также не заявляется как полностью совместимый с форматом проверки checksum-утилит: отдельного режима чтения списка хешей нет.

### 10.10. Ошибка вывода и код завершения

Потенциальная проблема: программа рассчитала верный хеш, но не смогла передать его приёмнику и всё равно вернула успех. Автоматический вызывающий код мог бы считать отсутствующий или повреждённый вывод успешным результатом.

Мера: `main` вызывает `fflush(stdout)` и проверяет индикатор ошибки. При отказе возвращается неуспешный код. Проверка `/dev/full` упражняет именно этот путь. Диагностика идёт в stderr, то есть не смешивается с нормальным результатом в stdout.

Граница: гарантируется обнаружение проверяемого отказа потока, а не отмена уже записанной части строки, сохранение данных на физическом носителе или доставка сообщения в тоже неисправный stderr. Код завершения и stdout нужно рассматривать вместе: валидной строкой успешного результата считается вывод успешно завершившегося процесса.

### 10.11. Проверки сборки и санитайзеры

Предупреждения компилятора помогают заметить типовые дефекты до запуска. AddressSanitizer добавляет проверки адресных обращений, UBSan ряд проверок неопределённых операций. Их назначения и флаги описаны в [документации GCC по инструментированию](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html).

При подготовке этого документа обычный набор `make test` прошёл: 8 тестовых методов, включая 171 общее сравнение хешей и проверки ошибочных путей. Диагностический набор запускается командой:

```sh
ASAN_OPTIONS=detect_leaks=0 UBSAN_OPTIONS=halt_on_error=1 make sanitize
```

`ASAN_OPTIONS=detect_leaks=0` отключает проверку утечек LeakSanitizer, которая не работает под ptrace в используемой среде. Адресные проверки остаются включены. `UBSAN_OPTIONS=halt_on_error=1` просит UBSan останавливать процесс при обнаруженной проблеме вместо продолжения после сообщения.

Обе сборки прошли этот набор при подготовке документа; AddressSanitizer и UBSan не сообщили об ошибках. Это относится к выполненным сценариям и не доказывает отсутствие всех ошибок. Сертификация криптографического модуля и проверка утечек в этом запуске не проводились.

### 10.12. Какие защиты здесь отсутствуют

Файловый путь открывается обычным `fopen`. Символические ссылки разрешены, ограничение пути выбранным каталогом не вводится, права доступа предоставляет ОС. Для локальной утилиты пользователь выбирает файл сам. Программа не должна описываться как сервис, безопасно исполняющий чужие запросы на чтение с повышенными привилегиями.

Файл не блокируется и не копируется в снимок. Если его содержимое меняется во время чтения, хеш относится к реально полученной последовательности байтов, которая может не совпасть ни с одной устойчивой версией файла. Тесты используют неизменяемые на время расчёта данные.

Секретного ключа у этой хеш-функции нет. Программа не реализует HMAC, подпись или проверку доверенности эталона. Злоумышленник, способный заменить и файл, и опубликованный хеш, может просто пересчитать отпечаток. Для проверки подлинности нужен доверенный источник ожидаемого хеша либо отдельный механизм аутентификации.

Буфер и временные слова не стираются специальным способом перед возвратом. Поэтому программа не обещает защищать прочитанные секретные данные от анализа памяти, swap или дампа процесса. `digest` тоже не является скрываемым ключом: он намеренно выводится пользователю.

Аудит постоянного времени не проводился. Индексы слов и число раундов задаются алгоритмом, но это наблюдение о коде не является доказательством отсутствия всех побочных каналов. Отдельные меры аппаратной защиты, изоляции процесса и криптографической валидации не реализованы.

Флаги `-fstack-protector`, `_FORTIFY_SOURCE`, отдельные настройки PIE/RELRO и другие способы усиления бинарника явно этим Makefile не включаются. Некоторые настройки могут быть стандартными для конкретного компилятора и окружения, но их нельзя приписывать этому проекту без проверки. Реально заданные здесь средства: предупреждения и отдельная инструментированная сборка.

## 11. Как показать работу преподавателю

Из корня проекта:

```sh
make
make demo
make test
```

`make demo` покажет размер и хеш каждого примера, вывод OpenSSL и итог сравнения. HTML, скриншоты и сохранённые отчёты для этого не нужны.

Для самостоятельного показа малого файла:

```sh
wc -c examples/small.txt
./build/sha3sum examples/small.txt
openssl dgst -sha3-256 examples/small.txt
```

В малом файле три байта `abc`. Значения хеша у собственной программы и OpenSSL должны совпасть, хотя оформление строки различается.

Для большого файла:

```sh
wc -c examples/large.bin
./build/sha3sum examples/large.bin
openssl dgst -sha3-256 examples/large.bin
```

Размер большого примера равен 2 097 152 байта. Наблюдавшийся результат:

```text
af542bd8dc97a22126445bee8a6acdf333eacf88baa4100abc03d92f46fe155e
```

Затем можно передать заведомо отсутствующий путь: программа завершится с отказом и сообщит `cannot open`, не выдавая хеш. В оболочке `echo $?` сразу после запуска показывает код предыдущей команды; после другого действия он уже относится к этому другому действию.

## 12. Вопросы, которые помогают проверить понимание

### Почему в программе два размера: 8192 и 136?

8192 относится к чтению файла, 136 к обработке сообщения алгоритмом. Буфер чтения можно менять независимо от алгоритма, если передавать все прочитанные байты. Rate менять произвольно нельзя. Поле `pos` связывает несколько чтений, когда блок не завершился на границе буфера.

### Почему нельзя просто сделать XOR всех байтов и вернуть результат?

Такое выражение потеряло бы порядок большого количества данных и было бы легко получить одинаковый результат для разных файлов. В программе между блоками выполняется полная 24-раундовая перестановка, а в конце добавляется однозначно определённое окончание. XOR является только способом добавить вход в состояние.

### Почему состояние не обнуляется после каждого блока?

Оно хранит влияние предыдущих байтов. Обнуление разорвало бы эту связь: более ранние блоки перестали бы влиять на оставшееся вычисление. `pos = 0` обозначает начало добавления следующего блока к уже существующему состоянию.

### Почему нужно XOR для padding, а не присваивание?

Даже незаполненные байтами текущего сообщения позиции состояния могут содержать значения от предыдущей перестановки. Дополнение является ещё одним блоком входа и должно добавляться к этому состоянию. Присваивание затёрло бы предыдущие значения.

### Почему нельзя проверить `feof` один раз перед циклом?

Индикатор EOF сообщает о результате уже выполненной попытки чтения, а не предсказывает наличие будущих данных. Поэтому сначала `fread`, затем проверка ошибки, затем обработка байтов и проверка EOF.

### Что означают `0` и `-1` у файловой функции?

Это её внутренний контракт успеха и отказа. Отрицательное значение не является хешем. Хеш записывается в `digest`, а причина отказа хранится в `errno`. У `main` другой интерфейс: он возвращает `EXIT_SUCCESS` или `EXIT_FAILURE` операционной системе.

### Почему `NULL` недостаточно для полной проверки указателя?

Ненулевой адрес может быть неправильным, уже освобождённым или указывать на слишком маленький объект. Обычный C-указатель не несёт размера и времени жизни объекта. Здесь корректность внутренних вызовов следует из того, что `main` создаёт массив на 32 байта и использует открытый поток.

### Что конкретно можно назвать защитой реализации при сдаче?

Потоковое чтение фиксированным буфером; ограниченные индексы; беззнаковые 64-битные операции с допустимыми сдвигами; явный порядок упаковки байтов; проверка открытия, чтения, закрытия и вывода; отказ от успешного хеша при ошибке; постоянные форматные строки; экранирование ASCII-управления в пути; предупреждения и санитайзеры как средства проверки этих решений.

### Что можно утверждать по пройденным тестам?

На проверенных сообщениях собственная реализация даёт те же хеши, что эталонные вызовы, а проверенные ошибочные пути заканчиваются отказом. На этих запусках диагностические инструменты не обнаружили проверяемых ими дефектов. Утверждения об абсолютной безопасности, сертификации, независимости библиотечных реализаций или всех возможных платформах из этого не следуют.
